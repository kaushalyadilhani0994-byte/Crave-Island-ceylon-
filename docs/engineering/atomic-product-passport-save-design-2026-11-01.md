# Atomic product + QR passport save — implementation review (2026-11-01)

## Status and preservation boundary

Implemented on `review/atomic-order-idempotency` only. This is not live production code yet.

The existing V18 Owner Admin layout, OTP login, owner email allowlist, product form, storefront routes, and QR URL format are preserved. The work is wired behind the existing Owner Catalogue save action and existing Owner QR Passport panel. It does not add a second Admin or customer-facing controls.

No migration has been applied to Supabase. No product, passport, QR record, production deployment, or main-branch change has been made.

## Live schema facts inspected read-only

- `public.products` has UUID primary key generated by `gen_random_uuid()`; `qr_code` is nullable text with a UNIQUE constraint.
- Product fields used by the Owner Catalogue include name, description, category (text), price numeric, currency text, image_url, ingredients text, allergen_information text, batch_number, stock_quantity integer, low_stock_threshold integer, track_inventory boolean, expiry_date date, manufacturing_date date, storage_location text, is_active boolean.
- `public.product_passports` has UUID primary key, `product_id` text UNIQUE, `public_slug` text UNIQUE, ingredients text[], allergen_information text[], origin, batch_code, best_before date, storage_instructions, public_story, published boolean, manufacturing_date date.
- Both tables have RLS enabled.
- Authenticated browser role has no direct INSERT/UPDATE/DELETE table privileges on `product_passports`, so direct browser upsert is not a valid owner-save path even where owner RLS policies exist.

## Implemented transaction flow

### Owner Catalogue product save

The existing product form now calls `public.owner_save_product_passport(...)` once. The private helper performs product insert/update, passport upsert, QR URL assignment, and idempotency record write in one database transaction.

- Create forces the product to `is_active = false`; saving a draft never activates it.
- Update retains the existing active state.
- Product editor updates do not overwrite existing passport origin, public story, or published state.
- The canonical slug remains `cic-<lowercase product UUID>`.
- The canonical QR destination remains `https://craveislandceylonv18supabaseintegra.vercel.app/passport.html?slug=<slug>`.
- An owner/request UUID key serializes concurrent retries. Repeating the same request with the same payload returns the original result; reusing the key with different data is rejected.
- The browser keeps the request key after an interrupted response and preserves form values on failure. Editing the form clears the old key.

### Owner QR Passport publishing

The existing Owner QR Passport panel now calls `public.owner_update_product_passport(...)` once. Its private helper locks the product row, validates the payload and active state, upserts the passport, and updates the product QR destination in the same transaction.

- Publishing is rejected while the product is inactive.
- Product activation/deactivation is serialized against passport publication by a row lock.
- The UI preserves entered values if the RPC response is interrupted and allows a safe retry.
- QR destination copy, open, and print-label flows remain in the existing panel.

### Public QR route

`passport.html` remains a public read-only view. It requires a published passport and an active product. It does not expose owner/admin controls. `shop-qr.html` remains the separate shop-promotion QR and is not the product-specific passport QR.

## Function security architecture

- Public Data API wrappers are `SECURITY INVOKER`.
- Privileged transaction helpers live in the non-exposed `private` schema and are `SECURITY DEFINER`.
- Every function pins `search_path = ''`; objects are schema-qualified.
- Each helper checks `auth.uid()` and `private.is_approved_owner()`.
- Execute is revoked from PUBLIC and anon and granted only to authenticated.
- The private idempotency table has no grants to PUBLIC, anon, or authenticated; the helper accesses it as function owner.
- No broad `product_passports` table grants or service-role browser key are introduced.

The SECURITY DEFINER helpers bypass normal table RLS according to their owner privileges, so their explicit owner check and narrow execute grants are critical. This still requires independent staging validation and a security review before production.

## Required staging validation before release

1. Owner creates a product: exactly one inactive product, one passport, one matching QR URL.
2. Owner edits product: same UUID and slug; no duplicate passport.
3. Existing published passport remains published when the product editor updates ordinary product fields.
4. Product/passport/QR writes roll back together on an induced passport or QR uniqueness failure.
5. Same idempotency key + same payload returns the original product; same key + changed payload is rejected.
6. Non-owner authenticated user and anonymous caller are denied.
7. Invalid price, category, ingredients, stock, threshold, tracking flag, and malformed dates are rejected server-side.
8. Concurrent product deactivation and passport publication do not permit publication against an inactive product.
9. Public route displays only published passports for active products.
10. Scan a generated product QR on a separate phone and verify it opens the correct passport.
11. Print a physical label and verify QR readability at the intended print size.
12. Confirm no customer route or navigation exposes Owner Catalogue, Owner QR Passport, or Admin.

## Release blockers

- There is no disposable staging Supabase project available in this workflow. A Supabase development branch has a recurring hourly cost, and none has been created.
- No PostgreSQL execution, migration test, Supabase Security Advisor run, browser/mobile runtime test, real QR scan, or print test has been completed.
- Do not apply this migration to production or merge/deploy this branch until staging tests are completed and the owner explicitly approves the release.

## Decision

Keep the implementation on the review branch. Preserve production unchanged while completing static review and preparing a controlled staging/release checklist.

## Additional QR editor safety check

The Owner QR Passport selector now waits for the selected product's existing passport row to load successfully before enabling Save. If the lookup fails, Save stays disabled and the current saved passport is not replaced with blank/default values. A stale response from a previously selected product is ignored. This prevents a transient read/network error from accidentally clearing origin, story, allergens, or publication state.

## Read-only production schema recheck (2026-11-01)

A fresh read-only Supabase schema inspection confirmed that the existing live columns used by this implementation match the expected types: product primary key UUID; product QR URL text/unique; product price numeric; inventory integer/boolean fields; manufacturing/expiry dates; category name unique and active flag; passport product_id/public_slug unique text; passport ingredients/allergens text arrays; passport publication boolean and story/origin/storage fields. RLS is enabled on products, categories, and product_passports.

The existing `private.is_approved_owner()` helper was inspected read-only. It checks `auth.uid()` against an approved `staff_profiles` owner row and is SECURITY DEFINER with a pinned `pg_catalog, public` search path. The proposed migration calls this established helper from its own private owner-only transaction helpers. The new public RPC wrappers are not present in live production because the migration has not been applied.

The Supabase Security Advisor was also run read-only. It reported existing findings unrelated to this proposed migration (including the owner report cron config table with RLS but no policy and several existing anonymous-policy warnings). No live policy or permission changes were made as part of this review.
