# Atomic product + passport save — review design (2026-11-01)

## Status and preservation boundary

Design only on `review/atomic-order-idempotency`. No SQL, migration, Edge Function, product, passport, catalogue, QR, or production deployment was changed for this review.

The existing V18 Owner Admin layout, OTP login, owner email allowlist, product form, storefront routes, and QR URL format must remain unchanged. This work must be implemented behind the existing Owner Catalogue save action; it must not create a second Admin or customer-facing controls.

## Live schema facts inspected read-only

- `public.products` has UUID primary key generated by `gen_random_uuid()`; `qr_code` is nullable text with a UNIQUE constraint.
- Product fields currently used by the Owner Catalogue include name, description, category (text), price numeric, currency text, image_url, ingredients text, allergen_information text, batch_number, stock_quantity integer, low_stock_threshold integer, track_inventory boolean, expiry_date date, manufacturing_date date, storage_location text, is_active boolean.
- `public.product_passports` has UUID primary key, `product_id` text UNIQUE, `public_slug` text UNIQUE, ingredients text[], allergen_information text[], origin, batch_code, best_before date, storage_instructions, public_story, published boolean, manufacturing_date date.
- Both tables have RLS enabled.
- The current form writes the product first, then reads the existing passport, upserts the passport, and finally updates `products.qr_code`. These are separate requests.

## Failure mode

A network interruption, RLS denial, uniqueness conflict, or database error after the first request can leave:
1. a product row saved without a matching passport; or
2. product/passport details updated but the QR link not attached; or
3. an existing published passport partially refreshed while the product record has already changed.

The UI reports a partial failure, but the database is not automatically rolled back across those requests. Retrying can then create confusion or overwrite an existing published passport state.

## Recommended target: one transaction

Replace the three browser writes with one narrowly scoped Postgres RPC that performs all database writes in one transaction:

1. Verify the caller is authenticated and is an approved owner using the existing database-side owner helper (do not trust client email, user metadata, or a hidden button).
2. Validate required fields and bounds again in SQL, including positive price, allowed LKR currency, non-empty name/category/ingredients, whole non-negative stock/threshold, and manufacturing date not after best-before.
3. For create: insert the product as `is_active = false` regardless of client input. Generate the UUID in Postgres.
4. Build the stable slug using the existing convention `cic-<lowercase product UUID>`.
5. Upsert the passport by `product_id`, preserving existing `origin`, `public_story`, and `published` values on edit. Do not silently publish a draft.
6. Attach the canonical public passport URL to `products.qr_code` in the same transaction. Keep the current route shape `/passport.html?slug=<slug>`.
7. Return the saved product UUID, slug, QR URL, and whether the operation created or updated a row.
8. Any exception must roll back product, passport, and QR changes together.

For updates, require a product UUID and update only that product. Preserve its current `is_active` value; never let this save action activate a draft. Preserve published passport state but ensure the public passport page's existing active-product/published-passport gate remains in force.

## Function security requirements

- Prefer `SECURITY INVOKER` so existing RLS policies remain in force.
- Confirm the live approved-owner SELECT/INSERT/UPDATE policies and table grants support every statement before implementation. Do not add broad grants as a shortcut.
- If invoker execution cannot safely perform the transaction, stop and redesign; do not reflexively switch to SECURITY DEFINER.
- If a definer helper is genuinely unavoidable, place it in the non-exposed `private` schema, pin an empty search_path, schema-qualify every object, explicitly check `auth.uid()` against the approved-owner helper, revoke EXECUTE from PUBLIC/anon, and grant only the exact intended caller. Review the bypass-RLS consequences before proceeding.
- Never place a service-role key in browser code.
- Keep the function's execute grants least-privilege and run Supabase Security Advisor after any eventual staging migration.

## Frontend integration

- Keep the existing form fields, button labels, success/error message area, draft behavior, and edit flow.
- Replace the product INSERT/UPDATE + passport UPSERT + QR UPDATE sequence with one `client.rpc(...)` call.
- Do not clear the form until the RPC confirms the transaction committed.
- If the response is lost after commit, the user should be able to refresh and find the saved product/passport/QR rather than creating a second product. Consider an explicit operation key for create retries if the chosen RPC contract does not otherwise make create idempotent.
- On error, keep form values and show a safe, concise error; never report success until the RPC response confirms commit.
- Continue to call the existing catalogue refresh only after confirmed success.

## Required staging test matrix

1. Owner creates a product: exactly one inactive product, one passport, one matching QR URL.
2. Owner edits product: same product UUID, same slug, QR remains correct, no duplicate passport.
3. Existing passport with `published=true`: edit preserves published state and origin/story; all product and passport fields commit together.
4. Force passport insert/upsert failure: product insert/update and QR change all roll back.
5. Force QR uniqueness conflict: product and passport changes roll back.
6. Non-owner authenticated user: RPC denied; no row changes.
7. Anonymous caller: RPC denied.
8. Invalid price, missing ingredients/category/name, negative/non-integer stock, malformed dates: rejected server-side.
9. Simulate network response loss after commit, then retry: no duplicate product.
10. Confirm public passport remains read-only and requires both active product and published passport.
11. Confirm no customer route or navigation exposes Owner Catalogue or Admin.
12. Confirm existing QR scanner resolves to the same public passport route.

## Open implementation prerequisites

- Recover the exact live product/passport RLS policies and grants before choosing invoker function privileges.
- Confirm the canonical site origin used to construct QR URLs; avoid accepting arbitrary origin from the browser.
- Decide and test an idempotent create-retry key so a lost RPC response cannot create duplicate draft products.
- Build and test against a disposable Supabase project with dedicated owner/non-owner accounts. No disposable project is currently available in this workflow.

## Decision

Do not merge or deploy a partial client-side compensation workaround. Implement the single-transaction RPC only after exact policy/grant inspection and isolated staging tests. No production schema or data change is authorized by this design note.

## Critical live privilege finding (read-only verified 2026-11-01)

The live role/table privilege check found a more immediate blocker than the multi-request transaction design:

- `authenticated` has SELECT on `public.product_passports`.
- `authenticated` does **not** have INSERT, UPDATE, or DELETE table privilege on `public.product_passports`.
- RLS policies exist for approved-owner INSERT/UPDATE/DELETE and team certificate permissions, but RLS policies do not grant SQL table privileges by themselves.
- `products` does grant authenticated INSERT/UPDATE/SELECT, with owner/team RLS policies.

The existing browser save sequence first commits the product INSERT/UPDATE, then attempts passport UPSERT. Because UPSERT needs INSERT and UPDATE privileges, the passport write is blocked at the SQL privilege layer before its RLS policy can authorize it. This can leave a hidden product draft (on create) or updated product fields (on edit) without the corresponding passport/QR refresh. This is a source + live privilege diagnosis; no live save was attempted.

Do not fix this by adding broad privileges without reconciling the intended staff permissions and the current RLS policies. The minimum candidate is authenticated INSERT and UPDATE on `product_passports`, with the existing approved-owner and certificate-team RLS policies remaining mandatory. DELETE is not required by the current save flow and should not be granted for this fix. Before any grant, verify whether team certificate-create/update permissions are intended to write these rows and confirm no permissive policy grants unintended access. Apply only in isolated staging, test owner/staff/customer/anon cases, and then obtain explicit production approval.


## Exact live policy and role check (read-only verified 2026-11-01)

The policy inspection confirms the current RLS intent on `public.product_passports`:

- Public `anon` and `authenticated` SELECT is restricted to `published = true` and a matching active product.
- Approved owners may SELECT all passports, INSERT, UPDATE (both USING and WITH CHECK), and DELETE.
- Team INSERT requires `private.has_staff_permission('certificates','create')`.
- Team UPDATE requires `private.has_staff_permission('certificates','update')` in both USING and WITH CHECK.
- Team DELETE requires `private.has_staff_permission('certificates','delete')`.
- Team SELECT requires catalogue.read or certificates.read.

A separate role privilege check reconfirmed:
- `anon`: no INSERT and no UPDATE on `product_passports`.
- `authenticated`: no INSERT and no UPDATE on `product_passports`.
- `authenticated`: INSERT and UPDATE on `products`.

This means a narrowly scoped `GRANT INSERT, UPDATE ON public.product_passports TO authenticated` would make the existing owner and team RLS policies enforce the intended row-level access; it would not itself authorize anon users, and DELETE would remain unavailable. However, the grant is still a live production schema change and has not been applied. It must be tested against owner, certificate-create/update staff, ordinary staff, customer-authenticated, and anonymous roles in an isolated staging project first.

The current browser save sequence is confirmed to commit the product INSERT/UPDATE before attempting the passport UPSERT. Therefore this privilege failure can create a partial product save. The immediate production-safe path is not to reorder browser writes: the durable correction remains a single transaction RPC. Do not enable product creation against the current live grants until the permission repair is approved and the save path is made transaction-safe.

## Review-branch implementation update (2026-11-01)

A first implementation is now present on `review/atomic-order-idempotency` only:

- New migration: `supabase/migrations/202611010001_atomic_owner_product_passport_save.sql`.
- Existing Owner Catalogue form now calls `public.owner_save_product_passport` once instead of issuing separate browser writes to products, passports and QR.
- The RPC is SECURITY DEFINER with a `pg_catalog`-only search path, checks `auth.uid()` against `private.is_approved_owner()`, and is executable only by `authenticated`; no anon execute grant is added.
- The private request ledger plus transaction-scoped advisory lock makes retries with the same owner/request key return the original saved product. Reusing a key with different payload is rejected.
- Product creation is forced inactive. Editing preserves the current active flag. Passport upsert preserves existing `origin`, `public_story`, and `published`; QR URL is generated from the canonical production origin and written in the same transaction.
- The browser retains the request key after a failed/uncertain response and clears it when the form is edited or a different product is selected. Form values remain on error.
- The original Admin layout, owner authentication code, fields, and button placement are not changed.

## QR passport publishing path review

A second write-path issue was found in the existing Owner · QR Passports panel: it also performed a direct browser upsert to `product_passports` followed by a separate `products.qr_code` update. The live grants reviewed earlier block those direct passport writes, and the two-step flow could leave the QR link and passport out of sync.

The review branch now adds `public.owner_update_product_passport(uuid, jsonb)` to the same review-only migration and routes the existing passport form through that RPC. It:
- exposes only SECURITY INVOKER wrappers; privileged implementations stay in the non-exposed private schema and require the approved owner;
- validates the product, ingredient list, dates, field lengths and publish state;
- refuses public publishing while the product is inactive;
- writes passport fields and the canonical production QR URL in one transaction;
- preserves the existing public passport route and customer-facing read-only behaviour.

The QR label and copy UI remain in the existing Owner · QR Passports panel. Both the catalogue-save and passport-publish browser flows no longer write directly to `product_passports`.

Static V8 syntax checks pass for the modified JavaScript files. The function design follows Supabase guidance to keep SECURITY DEFINER functions out of exposed schemas and use an empty search path. No SQL has been executed, no QR has been physically scanned, and no production data/schema/deployment has been changed. Staging execution and the owner/staff/customer/anon permission matrix remain mandatory before release.
